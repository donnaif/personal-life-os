# ARCHITECTURE DECISIONS — قرارات المعمارية

تنسيق: ADR مختصر (القرار، السياق، البدائل، النتيجة).

---

## ADR-0001 — لغة وأدوات المشروع الموحّدة
**القرار:** TypeScript في كل الطبقات (core، api، web، desktop). Node.js كوقت تشغيل.
**السياق:** Node 24 متوفر، والمشاريع القائمة كلها Node/Next → توحيد يقلل المخاطر ويسهّل المشاركة.
**البديل:** Python/C#/Go — مرفوض لعدم اتساقه مع البيئة.

## ADR-0002 — Monorepo بـ npm workspaces
**القرار:** monorepo: `packages/core` (منطق نقي)، `apps/api`، `apps/web`، `apps/desktop`.
**السبب:** مشاركة منطق الجدولة/الأنواع بين الخادم والويب وسطح المكتب.
**الرفض:** pnpm/yarn (غير مثبتين) → npm workspaces (متوفر).

## ADR-0003 — قاعدة البيانات: SQLite معزولة (Drizzle ORM)
**القرار:** SQLite داخل المشروع عبر Drizzle ORM، مع مخطط قابل للترحيل لاحقًا إلى PostgreSQL.
**السبب:** Postgres المشترك يتطلب كلمة مرور ولا نريد لمس بيانات الآخرين؛ الذاكرة محدودة؛
SQLite مثالي لمستخدم واحد + مزامنة لاحقًا.
**البديل:** Postgres المشترك — يحتاج موافقة وسر، ويرفض الآن.

### تحديث ADR-0003 (2026-10-18)
**القرار المحدّث:** استخدام محرّك **`node:sqlite` المدمج في Node 24** مع طبقة استعلامات
مُعاملة (prepared statements) بدل Drizzle في المرحلة الأولى.
**السبب:** `node:sqlite` مدمج (لا اعتماديات native، لا أدوات بناء، لا خطر توافق على Windows
Server)، وهو أسرع وأخف على الذاكرة من ORM كامل، والاستعلامات المُعاملة تمنع حقن SQL.
**مسار الترقية:** المخطط SQL قياسي؛ يمكن إدخال Drizzle/Kysely أو الترحيل إلى PostgreSQL لاحقًا
دون تغيير الواجهات العامة. يُوثَّق أي تغيير كـ ADR جديد.

## ADR-0004 — الخادم: Fastify + TypeScript
**القرار:** Fastify لخدمة REST + WebSocket (لاحقًا للمزامنة الحيّة).
**السبب:** متسق مع `musicbots` (Fastify)، سريع، خفيف، دعم schema/validation مدمج.
**البديل:** Express (أقدم، أقل أداء)، NestJS (ثقيل على الذاكرة).

## ADR-0005 — الويب: Next.js (App Router) + Tailwind + RTL
**القرار:** Next.js + TypeScript + Tailwind CSS، دعم RTL والعربية افتراضيًا، i18n منظم.
**ملاحظة:** الصفحات تُبنى بـ `next build` وتُشغَّل عند الحاجة (قيد الذاكرة).

## ADR-0006 — سطح المكتب: Electron
**القرار:** Electron (بدل Tauri) لأن Rust غير مثبت.
**القدرات:** إشعارات أصلية، تشغيل في الخلفية، مؤقتات، تخزين محلي SQLite، مزامنة، تحديث آمن.

## ADR-0007 — Android: Kotlin + Jetpack Compose (مؤجل)
**القرار:** تطبيق أصلي Kotlin/Compose + WorkManager/AlarmManager + Room، **يُبنى لاحقًا**.
**السبب:** Android SDK/Gradle غير مثبتين (تنزيل كبير) → يحتاج موافقة. لا نستخدم WebView بديلًا.

## ADR-0008 — منطق المجال داخل `packages/core` (نقي، قابل للاختبار)
**القرار:** الجدولة، التكرار، الجلسات، المؤقت، اكتشاف التعارض، الحسابات الزمنية، التقارير =
دوال نقية بلا I/O، مُختبَرة بـ Vitest. تُستهلك من كل الأطراف.
**السبب:** يضمن الاتساق بين المنصات ومنع تكرار المنطق.

## ADR-0009 — المزامنة: آخر-كاتب-يفوز على مستوى الحقل + change log + UUID
**القرار:** معرفات UUID، حقل `version`/`updatedAt`، سجل تغييرات تصاعدي، وde-dup عبر
`operationId`. سياسة التعارض موثقة لكل نوع بيانات.
**السبب:** يمنع فقدان بيانات ويمنع التكرار عند إعادة الإرسال.

## ADR-0010 — الأمان: مصادقة واحدة + أسرار في .env فقط
**القرار:** مستخدم واحد مبدئيًا (قابل للتوسع)، JWT للوصول + refresh، bcrypt/argon للتخزين،
تحقق مدخلات على الخادم (Zod)، تحديد معدل الطلبات، لا أسرار في Git.

## ADR-0011 — لا Docker: تشغيل أصلي + PM2 مخصص
**القرار:** Docker غير مثبت → تشغيل Node أصليًا. عند الحاجة لـ PM2: `--prefix` و`ecosystem`
خاص باسم `lifeos-*` فقط.

## ADR-0012 — إعادة الجدولة: الجلسات المخزَّنة وقت مشغول، والتاريخ لا يُمحى
**القرار:** أي نداء جدولة (`/tasks/:id/plan` و`/schedule/plan`) يمرّر الجلسات المخزَّنة
كـ `busy` للمحرك، ويستثني منها فقط الجلسات **غير المبدوءة** (`planned`) الخاصة بالمهام
التي تُعاد جدولتها. الحذف قبل الإدراج يقتصر على `status = 'planned'`، والمهام المنتهية
(`completed`/`cancelled`) لا تُلمس في الخطة الكاملة.
**السياق:** الاختبار اليدوي كشف تداخلًا مزدوجًا عند إعادة الجدولة، وأن `persist` كان يمحو
سجل الجلسات المنتهية (فقدان بيانات).
**النتيجة:** لا تداخل بعد إعادة الجدولة، والمهام قابلة لإعادة الجدولة دون خسارة السجل.

## ADR-0013 — الواجهة: React + Vite على 3101 مع وكيل `/api`
**القرار:** `apps/web` = React 19 + Vite، منفذ `127.0.0.1:3101`، وVite يوكّل `/api`
إلى `127.0.0.1:3100` مع إزالة البادئة → نفس الأصل، بلا CORS في التطوير.
**السبب:** فصل النشر (الواجهة ملفات ثابتة، الـAPI عملية Node) مع بساطة التطوير.
**بديل مرفوض:** Next.js (ADR-0005) — يحتاج خادمًا ووقت بناء أثقل ولا حاجة له هنا.

## ADR-0014 — تطبيق سطح المكتب: غلاف Electron + خادم loopback ثابت المنفذ
**القرار:** `apps/desktop` غلاف Electron يعيد استخدام مخرجات `apps/web/dist` كما هي، ويشغّل
خادمًا محليًا على `127.0.0.1:3105` يخدم الملفات الثابتة ويوكّل `/api` إلى الـAPI مع إزالة
البادئة (مطابق لوكيل Vite). تُجرَّب منافذ بديلة (3106، 3107، 3102، 3103) عند انشغال المنفذ،
ثم منفذ يعيّنه النظام كحل أخير.
**السبب:** المنفذ هنا هو أصل الواجهة (`http://127.0.0.1:<port>`) الذي يحدّد نطاق `localStorage`.
منفذ عشوائي لكل تشغيل يعني أصلًا مختلفًا ⇒ جلسة ومظهر مفقودان عند كل إقلاع (عيب حقيقي ظهر في
أول تحقّق فعلي للحزمة). لذلك: منفذ ثابت + نقل الرمز إلى مخزن الملف الشخصي (أدناه).
**بديل مرفوض:** `file://` — يمنع `fetch` عاديًا وCSP وعزل الأصل. وبروتوكول مخصّص (`app://`) —
أنظف أمنيًا لكنه يعيد كتابة طبقة الخدمة والوكيل بلا مقابل في هذه المرحلة.
**ملاحظة أمنية:** الخادم على `127.0.0.1` فقط، بلا `0.0.0.0`، وكل الطلبات تمر بفحص المسار
داخل جذر الويب (حماية اجتياز المسار).

## ADR-0015 — مخزن رمز التحديث: `safeStorage` + ملف في مجلد التطبيق
**القرار:** رمز التحديث يُشفَّر عبر `safeStorage` (DPAPI على Windows) ويُخزَّن في
`desktop-state.json` داخل مجلد التطبيق — لا في `localStorage`. الجسر يعرض `secureStorage`
و`tokenCrypto`، والواجهة تختار: desktop ⇒ مخزن الملف+التشفير، متصفح ⇒ `localStorage` كما هو.
**السبب:** `localStorage` مرتبط بالأصل (منفذ الخادم المحلي) ولا يوفّر تشفيرًا؛ فتغيّر المنفذ أو
تحديث التطبيق يُفقد الجلسة. كما أن نصًا صريحًا على القرص مرفوض.
**النتيجة:** الجلسة تبقى بعد إعادة التشغيل (مُتحقَّق منه: تشغيل ثانٍ يبدأ «مسجَّلًا» بلا دخول)،
والملف لا يحتوي إلا `enc:…`. عند تعذّر التشفير (بيئة بلا DPAPI) يبقى التطبيق عاملًا ويُعلن ذلك
(`getInfo().encryptionAvailable`) بدل الادّعاء.
**قابلية النقل:** الملف مشفَّر بمفتاح المستخدم ⇒ نسخه إلى جهاز آخر لا يكفي لفك التشفير (سلوك مقصود).

## ADR-0016 — إشعارات Windows: اختيارية (opt-in) ومقيدة
**القرار:** لا يُعرض أي إشعار قبل تفعيل المستخدم من الواجهة/القائمة. الفحص كل 60 ثانية عبر
جسر IPC، مع نافذة 10 دقائق قبل الموعد، وحاجز 5 دقائق يمنع إشعار جلسة فائتة، وسقف 3 إشعارات
لكل فحص، ومنع تكرار دائم بـ`notifiedSessionIds` (سقف 200 معرّفًا) في ملف الإعدادات.
**السبب:** الطلب نصّ على «إشعارات اختيارية بلا تنبيهات غير مرغوبة»، ومنع التكرار يمنع إغراق
المستخدم عند إعادة تشغيل التطبيق أو تكرار الفحص.
